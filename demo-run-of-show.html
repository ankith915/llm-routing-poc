Before you hit record

Two of these are not optional. The Groq free-tier ceiling makes a live experiment run take about three and a half minutes of dead air, and a cold database can make the first page load fail outright.

Do not run the experiment live on camera

On the free Groq plan an 18-query run takes roughly 3m30s, most of it rate-limit back-off. That is longer than this entire video. The results are already in the production database — open the dashboard and they are simply there.

If you want to show a run happening, start it, record ten seconds of the progress bar moving, then cut. Never wait it out.

  • Load the dashboard 5 minutes early

    If the Postgres instance sleeps when idle, the first request wakes it and can be slow or error. Get that out of the way before recording.

  • Confirm the results are showing

    The overview should show results for all three strategies and the compression panel beneath the comparison table. If it is empty, someone re-ran with a cleared store — you will need to re-run and wait.

  • Close everything with a key in it

    Terminal, .env, the Vercel dashboard, your password manager. The .env file has live Groq and OpenAI keys in plain text.

  • Hide bookmarks and notifications

    Browser in a clean window, do-not-disturb on. Zoom the page to about 125% so text is legible after compression.

  • Pre-type the demo query

    Have What is the current CPU usage of payment-api? ready to paste. Typing on camera is dead time.

The problem

On screen

You say

"Most teams building on large language models send every request to their best available model. It is the safe default, and it is expensive — you pay premium prices for questions that a much smaller model would answer perfectly well."

"This project tests a simple claim: that you can cut inference cost substantially without giving up answer quality, by choosing the model per request instead of picking one for everything."

If they ask

Prepared answers for the questions most likely to come back. The first one is the one I would expect your project manager to spot.

Why isn't the "intelligent" router clearly better than the simple keyword one?

On the live dashboard intelligent saves 62.6% and rule-based 58.5% — but on other runs of the same 18 questions the order has flipped. Three honest reasons, and you should give all three.

Sample size. Eighteen queries. A single question routing differently moves the number by several points, so the gap between the two — in either direction — is not meaningful at this n.

The rules are fitted to this dataset. The keyword heuristics were written against these exact 36 questions. That is close to grading your own homework — they will not transfer to real user phrasing, where the same intent arrives worded fifty different ways.

The intelligent router pays a toll. It spends a small model call on every request to make its decision, and that cost is charged against it in the comparison. The keyword router is free to run.

The honest summary: on this dataset the two are within noise of each other; the intelligent router is the one that survives leaving the lab.

Is the quality grading trustworthy? It is an AI grading an AI.

It is an LLM judge, and that is a real limitation worth naming. Two things make it defensible: every question has a predefined expected answer and grading criteria written in advance, so the judge is comparing against a fixed reference rather than forming a free opinion. And the same judge, at temperature zero, grades all three strategies — so any bias it has applies equally and the comparison between strategies stays fair.

It would not be sufficient for a production quality bar. It is sufficient to detect a strategy that saves money by degrading answers, which is what it is there for.

Would this hold up on our real workload?

Unknown, and worth saying so plainly. The savings depend on the mix of easy versus hard requests. This dataset is roughly 40% simple, 33% medium, 28% hard. A workload that is nearly all hard reasoning will save far less; a support-triage or classification workload would very likely save more.

The mechanism is what transfers. The specific percentage does not, until it is measured on real traffic.

What does the routing decision actually look at?

The small router model returns a structured assessment: complexity, whether multi-step reasoning is required, how much context is needed, the quality bar, and any latency requirement. Code then picks the cheapest configured model that satisfies every one of those constraints — including hard limits like context window size and a latency ceiling.

The model never picks the model. It describes the request; deterministic code does the selection. That keeps the choice auditable, and you can change the tier lineup without retraining or re-prompting anything.

What happens when a provider fails mid-run?

The request retries, then falls back to another tier, and cost is attributed to whichever model actually produced the answer — so a fallback can never understate real spend. Four fallbacks fired during the run you are showing, and none of them are visible in the results.

Only a request that exhausts every tier counts as a failure. That is why the comparison has an even 18 / 18 / 18 split rather than gaps.

Did you evaluate context compression — Headroom, TOON?

Both, measured rather than quoted. TOON was rejected: on this data it costs 18–28% more tokens than the pipeline's existing line format, because that format is already denser than TOON's tabular encoding. The format the pipeline sends today is itself 25.8% cheaper than the naive JSON dump most teams ship.

Headroom was run as a proper A/B — every query and strategy once uncompressed, once compressed, 108 graded requests. It saves 17.6% of context tokens, about 10% of cost per request. The only transform it finds on this data folds timestamps into a shared prefix. gpt-4.1 reads that fine (4.59 → 4.61). The 20B cheap-tier model does not (4.64 → 3.57) — it misreads the incident timeline.

So the two levers interact: compression breaks exactly the queries routing sends to the weakest model. The conclusion is a policy, not a switch — compress for the medium and premium tiers, never for the cheap tier. That keeps the saving where it is free and removes the quality hit. It is the next thing to build.

Why these particular models?

Cheap and medium tiers run on Groq — gpt-oss-20b and gpt-oss-120b. Same model family, so the tier difference is genuinely capability and not vendor quirk. Premium is gpt-4.1 on OpenAI, and a small gpt-4o-mini does the routing and grading.

The tier lineup lives in a single config file. Swapping any model is a one-line change with no code touched — which is the point, because model availability changes constantly.

Do not do these on camera

  • Start a full experiment run and wait. Three and a half minutes of a progress bar will lose the room, and on the free tier it can look like the app has hung.
  • Open the terminal or .env. Live API keys in plain text. If a key appears on screen you must rotate it before publishing the video.
  • Show the Vercel dashboard. Environment variables, deployment logs and billing are all one click apart.
  • Read the cost figures as precise forecasts. Say "roughly two-thirds" rather than "62.6 percent will be saved". The precision invites a challenge the sample size cannot support.
  • Claim the premium model is worse. The mid-tier scoring higher is a genuine and interesting result on this dataset at n=14. It is not a general finding about GPT-4.1.
